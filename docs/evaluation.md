# 评测体系

改 chunk 大小、调 rerank 权重、换 embedding —— 这些事没有评测就是拍脑袋。
这套评测的目标只有一个：**让每次改动都有分数说话，而不是凭手感。**

跑一轮检索层只要 3 秒，所以调参时可以反复跑。

## 怎么跑

```bash
python eval/run_eval.py                 # 只测检索层（不调 LLM，秒级）
python eval/run_eval.py --gate on       # 单独评估规则门控的拦截效果
python eval/run_eval.py --full          # 端到端，含 LLM 生成与拒答（约 100 秒）
python eval/run_eval.py --only D        # 只跑某一类题（D=域外拒答）
```

结果写到 `eval/results/`，同时生成 Markdown 报告和 JSON 明细。
每次运行的快照会自动归档到 `eval/results/archive/`，那里有一份
[迭代时间线](../eval/results/archive/README.md)，记录**每次运行对应哪次改动**。

## 评测集设计

`eval/testset.csv` 共 30 题，四类，比例是刻意配的：

| 类型 | 题数 | 考什么 |
| --- | --- | --- |
| `direct` 直问 | 10 | 直接用概念名提问，检验基础召回 |
| `paraphrase` 换说法 | 8 | 不用原文术语，考查语义召回——**稀疏检索最容易挂在这里** |
| `multi` 跨文档 | 6 | 答案分散在两篇文档，考查多路召回 |
| `reject` 域外 | 6 | 3 个常识域外 + 3 个「邻近域」（技术相关但语料没有） |

域外题特意不全用「红烧肉」这种明显无关的：`Python 的 GIL`、`Kubernetes 调度策略`
这类技术话题词面上和语料有大量重叠，才真正考验门控。

> 题库基于 55 篇 AI 产品概念文档构建，**那批语料不在仓库里**（第三方内容）。
> 复现这些分数需要自备语料并填 `DOCS_DIR`；换成自己的题库时
> 复制 `testset.example.csv` 的格式即可。

## 指标口径

- **Hit@1**：第一名就命中正解文档的比例
- **Recall@K**：top-K 内出现任正解的比例（K 取 `TOP_K`）
- **MRR@10**：第一个正解排名的倒数，衡量排序质量
- **误杀率**：本该回答却被拒的比例 —— **这个比 Recall 更该盯**
- **拒答准确率**：域外问题被正确拒绝的比例

判分用的是「命中的是哪篇文档」，不是「答案像不像」。因为后者太主观，没法当回归指标。

两个实现上的原则：

1. **拒答判定在评测脚本里独立实现**，不 import `generate.py` 的正则 ——
   否则改正则就能改分数，等于自己给自己发合格证。
2. **每份报告带配置快照**（`dense_mode` / chunk / `top_k` / `min_coverage` / 模型），
   否则跑完不知道这个分数属于哪个配置。

## 基线（55 篇 / 489 片段）

| 口径 | Hit@1 | Recall@5 | MRR | 误杀率 | 拒答准确率 |
| --- | --- | --- | --- | --- | --- |
| 检索层 + 规则门控（仅稀疏） | 54.2% | 70.8% | 0.625 | **29.2%** | 66.7% |
| 检索层 无门控（仅稀疏） | 66.7% | 95.8% | 0.799 | 0% | N/A |
| 端到端 + qwen-plus（prompt 加固前） | 66.7% | 95.8% | 0.799 | 0% | 83.3% |
| 端到端 + qwen-plus（prompt 加固后） | 66.7% | 95.8% | 0.799 | 0% | **100%** |
| **检索层 无门控（+ 向量混合）** | **75.0%** | **100.0%** | **0.875** | 0% | N/A |
| **端到端 + qwen-plus（+ 向量混合）** | **75.0%** | **100.0%** | **0.875** | 0% | **100%** |

第一组是「为什么关掉规则门控」最硬的证据：门控把 Recall 从 95.8% 砍到 70.8%，
换来 66.7% 的拒答准确率；把判断权交给模型后，Recall 保持 95.8%，
拒答准确率反而升到 83.3%，且零误杀。

第二组是接入真 embedding 后的一次完整迭代，**所有指标同向改善、零回归**：

| | 稀疏检索 | + text-embedding-v3 混合 |
| --- | --- | --- |
| Hit@1 | 66.7% | **75.0%**（+8.3pt） |
| Recall@5 | 95.8% | **100.0%**（补上唯一漏召的 B04） |
| MRR@10 | 0.799 | **0.875** |
| 误杀率 | 0% | 0% |
| 拒答准确率 | 100% | 100% |

单题耗时从 3277ms 升到 3529ms（+252ms，向量编码 + RRF 多一路）。
这个代价换 8 个点的 Hit@1 值得；真要省，query 向量缓存已在同一进程内生效。

## Top-K 曲线

24 道正题，`gate=off`，混合检索 1 / 0.5 / 2：

| top_k | Recall@K | Hit@1 | MRR | 未召回 |
| --- | --- | --- | --- | --- |
| 1 | 75.0% | 75.0% | 0.750 | 6 道（A04 / A05 / B01 / B04 / B07 / B08）|
| 2 | **100.0%** | 75.0% | 0.875 | — |
| 3 / 5 / 8 / 10 | 100.0% | 75.0% | 0.875 | — |

**Recall 在 K=2 就饱和，2→10 完全不涨。** 默认 `TOP_K=5` 属于「够用且留 1.5 倍余量」
的保守值，不是最优点；真正的最优点在 2–3。

**Hit@1 / MRR 与 K 无关**（只取决于第一名）——所以调 K 只能救「正解完全没进上下文」，
救不了「排错位置」。这个区分很重要：如果你的问题是排序错，调 K 是白费。

链路里有**两把 K，是不同的东西**：

- `CANDIDATE_K=20`：三路各自只取前 20 条进 RRF，是**候选池上限**。
- `TOP_K=5`：重排后 + 每文档最多 3 片过滤，再取前 N 送进模型。

还有一个余量很薄的边界：`generate.build_context(max_chars=6000)` 是累计超过就 `break`
**静默丢弃**，不报警告。这批 wiki 的 chunk 远短于 `chunk_size=600`（实际 130–700 字），
`top_k=10` 时上下文最多 4244 字符，没触发。但换成长文档语料就会踩 ——
届时界面「检索过程」显示 10 条、模型实际只读到 8 条，引用编号 `[9][10]` 指向模型没读过的内容。
