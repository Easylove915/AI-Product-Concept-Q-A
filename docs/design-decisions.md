# 设计取舍与已知局限

## 拒答：让系统知道「什么时候不该答」

RAG 最容易被忽略、也最容易翻车的环节。检索层永远能返回 top-k 片段——哪怕知识库里
根本没有这个话题。如果直接把 5 条不相关的片段塞给模型，模型就会硬凑一个答案。

项目里准备了两层防线，**但不是同时生效，而是按能力分工**：

| 场景 | 用哪一层 | 原因 |
| --- | --- | --- |
| 配置了大模型 | 生成侧 prompt 约束（规则门控关闭） | 模型能读懂片段在讲什么，判断力远超词面统计 |
| 未配大模型（抽取式降级） | 检索侧规则门控 | 没有模型可依赖，只能靠词面兜底 |

切换逻辑在 `rag/pipeline.py`：`ask()` 与 `search()` 都用 `gate=not cfg.llm_enabled`。
两个入口必须同口径，否则会出现「ask 能答、search 却 0 命中」的自相矛盾。

### 第一层：检索侧的相关性门控

用「IDF 加权的查询词覆盖率」判断这个问题是否落在知识库范围内：

```
覆盖率 = Σ(命中词的 IDF) / Σ(查询词的 IDF)
```

不用简单命中比例，是因为「流程」「阶段」「怎么」这类高频词几乎每个片段都有，
命中它们说明不了任何相关性；而「RAG」「报销」这种低 DF 词才是判据。
覆盖率低于 `MIN_COVERAGE` 就直接返回空结果，由上层给出明确拒答说明。

### 第二层：生成侧的 prompt 约束

system prompt 第 4 条要求「片段中没有足够信息就直接回答知识库中没有，不要猜测」。
实测模型在这一层表现明显更好。问「限流阈值是多少」，它会回：

> 知识库中没有找到限流阈值的具体数值。片段[5]仅说明限流属于「贯穿全链路的横切关注点」，
> 技术实现为「高并发流量调度」，但未提供阈值设定（如 QPS、TPS 或每分钟请求数等具体数值）。

问「红烧肉要炖多久」，它直接回「该问题属于烹饪常识，不在提供的 AI 产品知识库范围内」。

### 为什么最终把规则门控关掉了

原计划是两层同时生效，实测发现规则门控会误杀正常问题：

| 问题 | 覆盖率 | 应该是 |
| --- | --- | --- |
| RAG 的完整流程分几个阶段 | 0.20 | 该答 |
| 红烧肉要炖多久 | 0.23 | 该拒 |

**外域的分数反而比内域高。** 因为中文没有分词器时，二元组切分会切出大量跨词边界的
伪词（「的完」「整流」「程分」「分几」），它们在语料里 df=0、IDF 最高，只要有一个没命中
就把覆盖率拉到底。这个指标再怎么调阈值都无法同时做到零误杀。

对 RAG 系统来说，**误杀比漏放伤害大得多**：漏放还有模型兜底，误杀则是用户问了个
明明在库里的问题却被拒绝。所以最终选择「有模型就不靠规则」。

## 已知局限

### 1. IDF 在这批小语料上没有区分度

489 个片段，中文二元组切分后几乎所有词都只出现在 1 篇文档里，
**IDF 中位数和最大值都是 5.79**，等于没有区分度。所以基于覆盖率的规则门控只能做粗筛。

这个局限后来用两条路绕开了：**门控交给模型判断**，**召回交给语义向量**。
但根源仍在——没有分词器，词面这一路永远切不准。换 jieba 是下一步。

### 2. 引用校验只到编号级

`verify_citations()` 只校验编号是否越界，不做实体级忠实度校验。
D03 那种「编号合法但主语被换掉」的情况，目前纯靠 prompt 撑着（见 [failure-cases.md](failure-cases.md)）。

### 3. 这不是一个 Agent

严格说它是 RAG 应用：`ask()` = 一次 `search()` + 一次 `answer()`，
没有 tool 定义、没有决策循环、没有多轮。所有问题都走同一条固定路径。

### 4. 并发与延迟

- `pipeline.ask()` 的 `with self.lock` 把 LLM 调用（约 3.5s）也包在锁里，
  `ThreadingHTTPServer` 的多线程实际被串行化。
- 无流式输出，`/api/ask` 一次性返回，qwen-plus 平均 3529ms 全程白屏。
- 无结果缓存，相同问题会重复检索 + 重复计费。

## 从 Demo 到可用系统，建议按这个顺序做

1. **先跑通链路**：用示例文档 + 抽取式答案，确认检索能命中、引用能对上。
2. **接真实文档**：看文档数量、片段数是否合理，检查分块有没有把表格或代码切断。
3. **接大模型**：对比抽取式和生成式答案，重点看引用编号有没有被模型编造。
4. **做评测集**：挑 20–30 个真实问题，人工标出「应该命中哪篇文档哪一段」，
   每次改动后跑一遍。这一步比换任何框架都值钱。
5. **按需升级组件**：文档过万片段 → 换向量库；召回不准 → 加 cross-encoder 重排；
   需要多跳推理 → 加查询改写 / 多轮检索；要多人用 → 换 FastAPI + 鉴权 + 异步任务。
6. **补工程化**：文档变更 Webhook 自动同步、索引版本化、缓存、日志与耗时监控、答案反馈按钮。

不要一上来就上 LangChain + 向量数据库 + 重排模型。先让最朴素的链路跑通并建立评测集，
才知道瓶颈到底在分块、召回还是生成。

## 常见坑

- **同步失败 403/404**：私有仓库没配 `GITHUB_TOKEN`，或分支名不是 `main`
  （系统会尝试 `main`→`master`，也可显式指定）。
- **没有匹配的文档**：检查 `GITHUB_PATH` 是否指错、扩展名是否在 `GITHUB_EXTS` 白名单里。
- **召回不相关**：中文查询词太短时先用完整短语；或调大 `TOP_K`、降低 `MIN_SCORE`；
  长期方案是接语义向量。
- **该答的问题被拒答了**：如果配了 `LLM_API_KEY`，规则门控本来就不生效，拒答是模型自己判断的，
  检查 `TOP_K` 是否太小导致片段没召回；如果是抽取式模式，把 `MIN_COVERAGE` 调小（0 表示关闭）。
- **拒答的答案里带着引用，是 bug 吗**：不是。模型为了说明「片段里只有 A 的示例、没有 B 的数据」，
  会引用片段作为解释依据。这类回答质量比一句干巴巴的「没有找到」更高。
- **答案里引用编号对不上**：模型没遵守格式，可换遵循指令更好的模型，或在 `generate.py` 里加一次重试。
- **文档改了但答案没变**：需要重新同步并重建索引（界面 ↻ 或 `python scripts/cli.py sync`）。
- **PDF 想接进来**：`pip install pypdf`，在 `ingest.py` 的 `_to_text()` 里加一个分支即可，其余代码不用动。
