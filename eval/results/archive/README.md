这里的每一次运行对应一次**具体改动**。按时间顺序读，就是一条完整的优化链路：
每次只改一个变量、跑同一套 30 题、看指标往哪动。

> 全部为本地实测（55 篇 wiki / 489 片段，`qwen-plus`，`chunk_size=600 / overlap=100`，`top_k=5`）。
> `eval/testset.csv` 与 `results/` 属于本地资产，不入库；`latest-*.md` 永远指向当前口径。

## 每次运行对应什么改动

**1 → 2：关掉规则门控。**
规则门控（IDF 加权词覆盖率 < 0.24 就拒答）把 Recall 从 95.8% 砍到 70.8%，误杀 29.2%，
换来 66.7% 的拒答准确率 —— 不划算。而且实测外域问题（红烧肉 0.23）的覆盖率
比内域问题（RAG 流程 0.20）还高，阈值怎么调都分不开。
结论：**有模型就别用规则门控**，改由 prompt 约束拒答（`rag/pipeline.py` 的 `gate = not cfg.llm_enabled`）。

**3 → 4 → 5：修 D03 示例数据污染。**
第 3 次跑出 83.3% 拒答准确率，唯一翻车的是 D03（问郑州天气，模型把文档里北京的示例数据
主体替换后当成事实答了出来）。第 4 次用 `--only D` 单独跑 6 道拒答题定位，确认 leak 16.7%
就来自 D03。第 5 次在 system prompt 加规则 6/7/8 后拒答准确率升到 100%，
且 Hit@1 / Recall / MRR / 误杀率四项全部不变。

**5 → 6：接 `text-embedding-v3`。**
第一版重排用 `max(词面分, 语义分)` 融合，Recall 补满到 100%（B04 那句同义改写终于召回了），
但 Hit@1 还停在 66.7%、MRR 反而掉到 0.833 —— 因为词面分的量级（上限 ~4.9）永远压过语义分（~2.4），
`max` 等于让词面继续独占排序权。

**6 → 7：融合方式从 `max` 改成相乘。**
只有两个因子同时高，才算真命中。Hit@1 66.7% → 75%，MRR 0.833 → 0.875。
收益来自组合方式本身，不是调参：缩放系数取 2 / 3 / 4 结果完全一致。

**7 → 8：端到端复测。**
确认生成层没有拖回国。所有指标同向、零回归，单题耗时 3277ms → 3529ms（+252ms）。

## 命名规则

```
<YYYYMMDD-HHMMSS>-<口径>[-<范围>].{md,json}
```

- 口径：`retrieval`（只测检索层，秒级）/ `full`（端到端，含 LLM，约 100 秒）
- 门控：`gateon` / `gateoff`（`full` 口径下门控由模型判断，不加后缀）
- 范围：默认全量 30 题；`onlyD` 表示 `--only D`，只跑了拒答题，此时正题指标为 0 属正常，别误读
